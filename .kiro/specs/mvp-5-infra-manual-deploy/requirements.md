# Requirements Document

## Introduction

Infrastructure provisioning and manual deploy validation for the PAGA MVP walking skeleton. This spec covers the AWS CloudFormation templates (network, EC2, S3+CloudFront, IAM), deploy scripts (CodeDeploy hooks), Nginx reverse proxy configuration, CORS hardening in the .NET API, and operational documentation (runbook + ADR). The goal is to have all infrastructure artifacts validated and ready to be applied, enabling the backend API and Angular SPA to run in production on a single EC2 instance with CloudFront in front.

## Glossary

- **CloudFormation_Stack**: An AWS CloudFormation stack that provisions and manages a group of related AWS resources from a YAML template.
- **Network_Stack**: The CloudFormation stack containing VPC, subnets, internet gateway, route tables, and the shared security group.
- **EC2_Stack**: The CloudFormation stack containing the EC2 instance definition with user data bootstrap script.
- **Frontend_Stack**: The CloudFormation stack containing the S3 bucket, Origin Access Control (OAC), and CloudFront distribution.
- **IAM_Stack**: The CloudFormation stack containing IAM roles and instance profiles for CodePipeline, CodeBuild, CodeDeploy, and EC2.
- **Security_Group**: An AWS EC2 security group that controls inbound/outbound traffic to the instance.
- **CloudFront_Prefix_List**: The AWS-managed prefix list `com.amazonaws.global.cloudfront.origin-facing` that identifies CloudFront edge IP ranges.
- **Parameter_Store**: AWS Systems Manager Parameter Store, used to store secrets as SecureString values.
- **OAC**: Origin Access Control — CloudFront mechanism to restrict S3 bucket access to the distribution only.
- **CodeDeploy_Hook**: A lifecycle event script executed by the CodeDeploy agent during application deployment (stop, install, start, validate).
- **Kestrel**: The cross-platform web server for ASP.NET Core, running the PAGA API on port 5000.
- **Nginx_Proxy**: Nginx configured as a reverse proxy, forwarding `/api` requests from port 80 to Kestrel on port 5000.
- **Idempotent_Migration_Script**: A SQL script generated by `dotnet ef migrations script --idempotent` that safely applies pending database migrations.
- **CORS_Policy**: Cross-Origin Resource Sharing configuration in the .NET API that restricts which origins may call the API.
- **Manual_Deploy**: The process of provisioning infrastructure by executing CloudFormation commands manually (not through a CI/CD pipeline).
- **Runbook**: Operational documentation with step-by-step instructions for deploying, validating, and troubleshooting the production environment.

## Requirements

### Requirement 1: Network Stack Provisioning

**User Story:** As a DevOps engineer, I want a CloudFormation template that provisions the network layer (VPC, subnets, internet gateway, route tables, security group), so that the EC2 instance has a secure and correctly routed network environment.

#### Acceptance Criteria

1. THE Network_Stack SHALL create a VPC with a CIDR block configurable via a template parameter.
2. THE Network_Stack SHALL create at least one public subnet within the VPC.
3. THE Network_Stack SHALL create an internet gateway attached to the VPC and a route table with a default route (0.0.0.0/0) to the internet gateway.
4. THE Network_Stack SHALL create a Security_Group that allows inbound TCP traffic on ports 80 and 443 only from the CloudFront_Prefix_List.
5. THE Network_Stack SHALL create a Security_Group rule that allows inbound TCP traffic on port 22 only from a CIDR provided as a required template parameter with no default value.
6. THE Network_Stack SHALL block inbound TCP traffic on port 5432 from any source.
7. THE Network_Stack SHALL export the VPC ID, public subnet ID, and security group ID for consumption by other stacks.
8. WHEN the template is submitted to `aws cloudformation validate-template`, THE Network_Stack SHALL pass validation without errors.

### Requirement 2: EC2 Instance Stack

**User Story:** As a DevOps engineer, I want a CloudFormation template that provisions an EC2 t3.micro instance with all runtime dependencies pre-installed, so that the PAGA API and PostgreSQL database can run on a single server.

#### Acceptance Criteria

1. THE EC2_Stack SHALL create an EC2 instance of type t3.micro running Amazon Linux 2023.
2. THE EC2_Stack SHALL import the VPC, subnet, and security group from the Network_Stack exports.
3. THE EC2_Stack SHALL associate the EC2 instance with the instance profile exported from the IAM_Stack.
4. THE EC2_Stack SHALL include a user data script that installs .NET 10 runtime, PostgreSQL 16 server, Nginx, the CodeDeploy agent, and the psql client.
5. THE EC2_Stack SHALL configure the PostgreSQL 16 service to start on boot, listen only on localhost (127.0.0.1), and create the application database.
6. THE EC2_Stack SHALL configure the database password by reading the `DB_PASSWORD` secret from Parameter_Store during user data execution.
7. THE EC2_Stack SHALL assign a public IP address (or Elastic IP) to the instance so CloudFront can reach it.
8. THE EC2_Stack SHALL accept the instance type as a parameter with a default of `t3.micro`.
9. WHEN the template is submitted to `aws cloudformation validate-template`, THE EC2_Stack SHALL pass validation without errors.

### Requirement 3: Frontend Stack (S3 + CloudFront)

**User Story:** As a DevOps engineer, I want a CloudFormation template that provisions an S3 bucket for the Angular SPA and a CloudFront distribution with proper routing, so that users access the frontend over HTTPS and API calls are proxied to the EC2 instance.

#### Acceptance Criteria

1. THE Frontend_Stack SHALL create an S3 bucket for static website hosting with a parameterized bucket name.
2. THE Frontend_Stack SHALL create an OAC and a bucket policy that allows only the CloudFront distribution to read objects from the S3 bucket.
3. THE Frontend_Stack SHALL create a CloudFront distribution with the default behavior pointing to the S3 bucket origin via OAC.
4. THE Frontend_Stack SHALL configure a cache behavior for the path pattern `/api/*` that forwards requests to the EC2 instance origin over HTTP (port 80).
5. THE Frontend_Stack SHALL configure the CloudFront distribution to return `/index.html` for HTTP error codes 403 and 404 with a 200 response code (SPA fallback).
6. THE Frontend_Stack SHALL use the CloudFront default domain name (*.cloudfront.net) without a custom domain or ACM certificate.
7. THE Frontend_Stack SHALL export the CloudFront distribution domain name and distribution ID.
8. WHEN the template is submitted to `aws cloudformation validate-template`, THE Frontend_Stack SHALL pass validation without errors.

### Requirement 4: IAM Stack

**User Story:** As a DevOps engineer, I want a CloudFormation template that provisions least-privilege IAM roles for all AWS services involved in the deployment pipeline and EC2 runtime, so that each service has only the permissions it needs.

#### Acceptance Criteria

1. THE IAM_Stack SHALL create a role for CodePipeline with permissions limited to invoking CodeBuild and CodeDeploy and reading/writing the pipeline artifact S3 bucket.
2. THE IAM_Stack SHALL create a role for CodeBuild with permissions limited to reading the source artifact, writing the output artifact, writing CloudWatch Logs, and performing S3 sync and CloudFront invalidation for the frontend.
3. THE IAM_Stack SHALL create a role for CodeDeploy with permissions limited to managing EC2 deployments and reading deployment artifacts from S3.
4. THE IAM_Stack SHALL create an EC2 instance profile with a role that grants read access to SSM Parameter Store parameters prefixed with `/paga/` and read access to the CodeDeploy artifact S3 bucket.
5. THE IAM_Stack SHALL avoid using wildcard (`*`) in the `Resource` field when the specific ARN is known or parameterized.
6. THE IAM_Stack SHALL export the instance profile ARN and the CodeDeploy role ARN for consumption by other stacks.
7. WHEN the template is submitted to `aws cloudformation validate-template`, THE IAM_Stack SHALL pass validation without errors.

### Requirement 5: Nginx Reverse Proxy Configuration

**User Story:** As a DevOps engineer, I want an Nginx configuration file that reverse-proxies API requests to Kestrel, so that the EC2 instance serves both static and dynamic traffic on port 80.

#### Acceptance Criteria

1. THE Nginx_Proxy SHALL listen on port 80 for all server names.
2. THE Nginx_Proxy SHALL forward requests matching the location `/api` to `http://localhost:5000`.
3. THE Nginx_Proxy SHALL forward the `Host`, `X-Real-IP`, and `X-Forwarded-For` headers to the upstream.
4. THE Nginx_Proxy SHALL forward the `X-Forwarded-Proto` header with value `$scheme` to the upstream.
5. THE Nginx_Proxy SHALL return a 502 Bad Gateway response when Kestrel is unreachable, rather than a connection timeout.

### Requirement 6: CodeDeploy Application Specification

**User Story:** As a DevOps engineer, I want an `appspec.yml` and associated lifecycle scripts (stop, install, start, validate), so that CodeDeploy can deploy and restart the PAGA API reliably.

#### Acceptance Criteria

1. THE appspec.yml SHALL specify the `os` as `linux` and define file mappings from the deployment artifact to the application directory on the instance.
2. THE appspec.yml SHALL define hooks for `ApplicationStop`, `BeforeInstall`, `ApplicationStart`, and `ValidateService` lifecycle events.
3. WHEN the `ApplicationStop` hook runs, THE stop.sh script SHALL stop the Kestrel systemd service gracefully.
4. WHEN the `BeforeInstall` hook runs, THE install.sh script SHALL copy the published application files to the target directory and execute the idempotent SQL migration script using `psql`.
5. WHEN the `ApplicationStart` hook runs, THE start.sh script SHALL start the Kestrel systemd service.
6. WHEN the `ValidateService` hook runs, THE validate.sh script SHALL send an HTTP GET request to `http://localhost:5000/health` and succeed only if the response status code is 200.
7. THE install.sh script SHALL read the database password from Parameter_Store to construct the `psql` connection string.

### Requirement 7: CORS Configuration for Production

**User Story:** As a backend developer, I want the .NET API CORS policy to accept requests only from the CloudFront distribution domain, so that no unauthorized origins can call the API in production.

#### Acceptance Criteria

1. THE CORS_Policy SHALL read allowed origins from configuration (section `Cors:AllowedOrigins`).
2. WHILE running in production, THE CORS_Policy SHALL authorize only the CloudFront distribution domain (e.g., `https://dXXXXXXXXXX.cloudfront.net`).
3. WHILE running in development, THE CORS_Policy SHALL authorize `http://localhost:4200` as the default origin.
4. THE CORS_Policy SHALL allow any HTTP header, any HTTP method, and credentials in cross-origin requests.
5. IF a request arrives from an unauthorized origin, THEN THE CORS_Policy SHALL reject the preflight request by omitting CORS headers from the response.

### Requirement 8: Secrets in Parameter Store

**User Story:** As a DevOps engineer, I want secrets stored in AWS SSM Parameter Store as SecureString, so that sensitive values are never committed to source control or exposed in templates.

#### Acceptance Criteria

1. THE Runbook SHALL document the creation of the following SecureString parameters: `/paga/jwt-key`, `/paga/db-password`, and `/paga/admin-password`.
2. THE deploy scripts SHALL read secrets from Parameter_Store at runtime using the AWS CLI or SDK, never from environment variables baked into templates or buildspecs.
3. THE CloudFormation templates SHALL contain no plaintext secret values, default parameter values for secrets, or hardcoded passwords.

### Requirement 9: Stack Creation Order and Cross-Stack References

**User Story:** As a DevOps engineer, I want the stacks to use CloudFormation exports/imports for cross-stack references, so that resources can be provisioned independently in the correct order.

#### Acceptance Criteria

1. THE Runbook SHALL document the stack creation order as: Network_Stack → IAM_Stack → EC2_Stack → Frontend_Stack.
2. THE EC2_Stack SHALL import the security group and subnet from Network_Stack and the instance profile from IAM_Stack using `Fn::ImportValue`.
3. THE Frontend_Stack SHALL accept the EC2 public IP or DNS as a parameter (or import) to configure the API origin in CloudFront.
4. WHEN a stack is created out of order, THE dependent stack SHALL fail with a clear missing-export error rather than provisioning incorrectly.

### Requirement 10: Operational Runbook

**User Story:** As a DevOps engineer, I want a runbook documenting step-by-step manual deploy instructions, so that the infrastructure can be provisioned and validated without relying on CI/CD.

#### Acceptance Criteria

1. THE Runbook SHALL include prerequisites (AWS CLI installed, profile `palaia` configured, required parameter store secrets created).
2. THE Runbook SHALL include the exact `aws cloudformation create-stack` commands for each stack in the correct order, with all required parameters.
3. THE Runbook SHALL include instructions for building and publishing the .NET API (`dotnet publish`), generating the idempotent migration script, and deploying manually to the EC2 instance.
4. THE Runbook SHALL include instructions for building the Angular SPA (`ng build --configuration production`) and syncing to S3 with CloudFront invalidation.
5. THE Runbook SHALL include a validation section that verifies `/health` returns 200 through CloudFront, the SPA loads, and API calls succeed.
6. THE Runbook SHALL include a troubleshooting section for common failures (security group blocking, Nginx misconfiguration, Kestrel not starting, database connection failure).

### Requirement 11: Architecture Decision Record

**User Story:** As a developer, I want an ADR documenting the single-instance architecture decision, so that the trade-offs of running API, database, and web server on one EC2 instance are recorded.

#### Acceptance Criteria

1. THE ADR SHALL follow the standard format: Title, Status, Context, Decision, Consequences.
2. THE ADR SHALL document the decision to co-locate the .NET API, PostgreSQL, and Nginx on a single EC2 t3.micro instance.
3. THE ADR SHALL state that this architecture is acceptable for an MVP/validation phase and list the trade-offs (single point of failure, no horizontal scaling, no managed database).
4. THE ADR SHALL reference the future path to separate concerns (RDS, ECS/Fargate, or multi-instance) when the application moves beyond MVP.

### Requirement 12: Template Parameterization

**User Story:** As a DevOps engineer, I want all CloudFormation templates to accept configurable parameters for environment-specific values, so that the same templates can be reused across environments without modification.

#### Acceptance Criteria

1. THE CloudFormation templates SHALL parameterize: environment name, VPC CIDR, SSH CIDR, instance type, S3 bucket name, and Parameter Store path prefix.
2. THE CloudFormation templates SHALL use a consistent naming convention for resources incorporating the environment parameter (e.g., `paga-{Environment}-vpc`).
3. THE CloudFormation templates SHALL provide sensible defaults for non-sensitive parameters (VPC CIDR `10.0.0.0/16`, instance type `t3.micro`) while requiring sensitive/environment-specific ones (SSH CIDR).

### Requirement 13: Health Endpoint Reachability

**User Story:** As a DevOps engineer, I want the `/health` endpoint to be reachable through the full infrastructure path (CloudFront → EC2 → Nginx → Kestrel), so that deployment validation can confirm end-to-end connectivity.

#### Acceptance Criteria

1. THE Nginx_Proxy SHALL forward requests to `/health` to the Kestrel upstream alongside `/api` routes.
2. THE Frontend_Stack CloudFront distribution SHALL route `/health` requests to the EC2 origin (included in the `/api/*` behavior or as a separate behavior).
3. WHEN the validate.sh script sends a request to the local `/health` endpoint, THE Kestrel application SHALL respond with HTTP 200 and a JSON body containing `{"status":"Healthy"}`.
